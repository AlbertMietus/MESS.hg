===============

You shouldn’t build a 350m skyscraper like a bike shed; likewise, 35M lines of Linux takes a different style than
``HelloWorld``.  All software starts small however; Linux fit on a single page, once.
|BR|
Sound architecture helps to scale! E.g. Linux is based on the *'Common Unix Architecture'*, with drivers, CPU abstraction,
file- & networking-IO, etc. Even version v0.0.1 of the Linux kernel used it.

Remember, a big codebase is a lot of work. Estimates suggest a product of Linux's complexity costs around **20,000 Sprints**.
|BR|
But, it always starts small and smooth; probably you know every line of ``HelloWorld``. But that approach doesn't
scale -- you can’t memorize 35M SLOC.

To scale, no single SW-engineer should ever get lost in a codebase. Otherwise nobody can add features, and the
system can't grow!

Grouping sources in (sub)directories along the architectural structure helps!
|BR|
Roughly, 80% of all Linux code is in the `drivers` directory. When you're not working on drivers, you can skip the biggest
portion of the code in a blink. This structure is everywhere.  To improve, for example, the real-time behavior of the
scheduler, you can skip more, like the hardware abstraction, and all I/O modules. Only about 0.2% of all code is for the
scheduler; and it's easy to find (in ``/kernel/sched/``:-).
|BR|
The real-time part of the scheduler is even smaller; it's less than 1/100 of 1% of the codebase. A manageable 2k lines.

Architecture brings structure, and the ability to find stuff. And with that, the option to change a few lines,
without reading most of the code.

Next time you start with something that potentially can become bigger than 5 lines: Start with a sound
architecture. Always make sure there is only one logical spot for all future lines. Then, one day, you can add as many
SW-bricklayers as you need for your “skyscraper”.
