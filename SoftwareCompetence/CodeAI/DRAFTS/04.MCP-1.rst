=======================
Agentic Coding with MCP
=======================

.. post:: 2026/10/05		
   :category: ScenerySketching
   :tags: CodeAI
   :location: Geldrop
   :language: en

   “Writing code” is more than just *writing text*. When human engineers work with code, they need a variety of tools to
   build (a **compiler**) and verify (several **test runners**) the software. We can enable LLMs to run these tools as
   well; this offers many benefits and can introduce huge risks.

   In this article, we introduce MCP, the protocol that enables *agentic AI*. But be warned! MCP is extremely powerful,
   and ---as an LLM has no conscience--- it will happily wipe all your work, or worse.  More on that in an upcoming
   article: :ref:`“MCP safety” <CodeAI-MCP2>`.
   |BR|
   Now we focus on how agentic coding fits into the scenery, and how we can speed up engineering by asking LLMs to run
   those tools for us.

   The open-source standard **MCP** is invented by Anthropic in 2024 and has become the widely supported standard.
   |BR|
   The terminology used in MCP can be a bit confusing, possible as the original use-case (‘context’) is currently
   completely outdated.

   Basically, your *LLM-IDE* (like Emacs, Claude, Copilot, etc ) sends an list of available tools. The LLM selects, and
   direct your LLM_IDE to run it with some parameters, and the result is send to the LLM again, who read it and either
   runs the next tool, or give an answer.

   MCP is open and flexible. It’s basically text, with a little bit of JSON structure; which is just text for an LLM.

Automating isn't new
====================

For years the software engineering world has been automating itself. Thirty years ago, we used tools like `cron` for a
*nightly build*. It did run a `script` to check-out a revision, run the compiler via a `Makefile`, and so on.  Gradually
that evolved into the current CI/CD environments. Nowadays every tool is run automatically via a configuration.

So, what's new with *agentic coding*?
|BR|
*Nothing* and **Everything**! The same tools are still used. But now a *’stochastic'* LLM is in charge of running
those tools. It might start the compiler, or a test-tool, etc receive the results. As it understand most errors and
warning, it can even fix the bug or rerun the tool with other options.

Again, the basic idea is the same --- even better, as the LLM can react more flexible than a tradition script.


Context is relevant
===================

**MCP**: *Model Context Protocol* has become the de facto protocol to run all kind of tools, from searching
the web, to running developers-tools on your computer. But it started with context.
|BR|
As an example, your LLM may need the docs of an library it want to use. Often it is inconvenient to supply them
proactively. With MCP, the LLM can request that context, by sending a request to your CodeAI environments (“LLM-IDE”)
who uploads it, and the LLM continues.

But, MCP is more flexible. It can also ask to search the internet --- the LLM has no direct web-abilities --- by
instructing the ‘LLM-server’ with an URL, and forward the web-page back to the LLM.

Develop & Change
================

Developing software is more then requesting more ‘context’. We need to change files and run tools. Fortunately, MCP is
flexible: it can run any (non interactive) tool. Executing your compiler is easy, but it also change, or save, files.
|BR|
In chat-mode you can also ask for some code, but you have to copy in manually into the correct file. With MCP that step
can be automated. When you provide a *‘patch’ tool*, your LLM wil send a patch. But you LLM can also work with a
*‘write’ tool* --- then it happily send the complete file. A typical LLM is cleaver enough to select a tool it can
use. Or misuse one, as we will see later.
