=======================
Agentic Coding with MCP
=======================

.. post:: 2026/10/05		
   :category: ScenerySketching
   :tags: CodeAI
   :location: Geldrop
   :language: en

   “Writing code” is more than just *writing text*. When human engineers work with code, they need a variety of tools to
   build (a **compiler**) and verify (several **test runners**) the software. We can also enable LLMs to run these
   tools; this offers many benefits and can introduce huge risks.

   In this article, we briefly cover *MCP*, the protocol that enables *agentic AI*. But be warned! MCP is extremely powerful,
   and ---as an LLM has no conscience--- it will happily wipe all your work, or worse.  More on that in an upcoming
   article: :ref:`“MCP safety” <CodeAI-MCP2>`.
   |BR|
   Now we focus on how agentic coding fits into the scenery, and how we can speed up engineering by asking LLMs to run
   those tools for us.

.. .. include:: ./sidebar-ScenerySketching.irst


.. sidebar:: Maps & Milestones
   :class: sidebar-ScenerySketching

   The open-source standard **MCP** (*Model Context Protocol*) is invented by Anthropic in 2024 and has become the
   widely supported standard.
   |BR|
   The terminology used in MCP can be a bit confusing, possibly as the original use-case (‘context’) feels currently
   outdated. Also, the words ‘Server’ and ‘Client’ are, though technically correct, inverted compared to what
   most people expect: The server is running on your computer, to start the tools on your computer. Only the LLM (acting as
   client) runs remotely.

   MCP is open and flexible. It’s basically text, with a little bit of JSON structure; which is just text for an LLM.

   Basically, your *LLM-IDE* (like Emacs, Claude, Copilot, etc ) sends a list of available tools. The LLM selects, and
   direct your LLM-IDE to run it with some parameters, and the result is sent  to the LLM again, who reads it and either
   runs the next tool, or give an answer.
   |BR|
   As you can see, it is all text-based, and so fits the LLM very well.

Automating isn't new
====================

For years, the software engineering world has been automating itself. Thirty years ago, we used tools like `cron` for a
*nightly build*. It did run a `script` to check out a revision, run the compiler via a `Makefile`, and so on.  Gradually,
that evolved into the current CI/CD environments. Nowadays, every developer-tool runs automatically as set by a
configuration file.

So, what's new with *agentic coding*? *Nothing* and *Everything*!
|BR|
The same tools are still used. But now the script, aka configuration, is replaced by an LLM. It can start the compiler,
or a test-tool, etc and receive the results. As it understands errors and warnings, it can even fix the bug and
rerun some tool with other options. And continue until it decides it ready.

Again, the basic idea is the same. Better ---some will say--- as the LLM reacts more flexibly than a traditional
script. Substandard, others will say, as the deterministic script, aka configuration, is replaced by a *stochastic*
LLM.
|BR|
Pick your own side; both arguments are legitimate.


Context is relevant
===================

**MCP** has become the de facto protocol to run all kinds of tools, from searching the web to running developer tools
on your computer. But it started with context.
|BR|
For example, your LLM may need the docs of a library it wants to use. As it was inconvenient to supply them all
proactively, an alternative reactive way was invented. With MCP, the LLM can request the info it needs by sending a request
to your CodeAI environments (“LLM-IDE”) that uploads it, such that the LLM has all context it needs.

But MCP is more flexible. It can also ask to search the internet --- as the LLM itself has no direct web abilities --- by
instructing your ‘LLM-IDE.’ with a URL and forwarding the web page back to the LLM. Or, for CodeAI, read the code, the
design document, etc.
|BR|
There are no limits --- also, reading the errors of a compile-job gives ‘context’.


Develop & Change
================

Developing software is more than requesting more ‘context’. We need to change files and run tools. Fortunately, MCP is
flexible: it can run any (non-interactive) tool. Give it a tool to save a text file, it is able to change code.
|BR|
In the old CodeAI-days, the LLM could also write code --- in chat mode. But, you had to copy in manually into the correct
file. With MCP that step is automated.

In this way, an LLM can support the programmer. And very similar, it can use a huge variety of rig to handle code.
|BR|
When you provide a *‘patch’ tool*, your LLM will send a patch. But you LLM can also work with a *‘write’ tool* --- then
it happily send the complete file. A typical LLM is clever enough to select a tool it can use. Or misuse one, as we
will see later.

Plan & Act
==========

A big change between the initial “chat” LLMs and ‘agentic AI’ is that it can act. However, there is one important step
in between ‘planning’. Originally, the chat just continues your story, generating the next (most likely) word, word for
word.
|BR|
Everybody will remember those examples where its answer started with ‘yes’ and continued arguing it should be no. As if there
is no backspace on an LLM.

That changed when ‘reasoning’ was discovered. The key here was a 2-step approach. Instead of sending the question to the
LLM directly, a bit of extra was added: *“Please don’t answer, but act as a project manager: write a plan on how to solve
it”* (and then execute it).
|BR|
Typically that plan is hidden for the user.  When you look to it, you will see the same kind of mistake and correct
approach --- like it any plan.

The next conceptual step is use a loop, instead of just 2 steps.
|BR|
So, we start with a plan, including some ‘reasoning’ on what data and tools are needed. Then the LLM write text, to run
a tool, and collects the data. And that repeats.

Again, most of those in-between “chats with itself” are hidden, but in many environments you can see them. Have a look,
its fun!
|BR|
Often, it will describe something like: Maybe I can use tool one, and tries it. When it fails, it writes that down,
re-plan, and tries the next one. And keeps “trying” until you run out of tokens or it thinks it is ready. --- We all
recognize this loop.

Coding: Engineering or Hacking?
===============================

GenAI made some big steps in a few years. Some people didn't even take the first step a: simple chat. Other are already
sure programming is outdated, as LLM can write software.
|BR|
And, when we follow the developments computers already mastered the concept of *hacking*; they do break-in into other
systems.

My quest is different: Are they becoming an *artificial (software) engineer?*
|BR|
Engineering isn't only about writing code. It's also about control, about craftsmanship. It takes years of study and
practice to understand how to construct an complicated machine.

Sometimes, the outcome of a 'Agentic Code job' is amazing. And, at the same time --- when we look under the bonnet, like
described above --- it feels like a bombshell.  When a (junior) coworkers behaves like that, we call it "try and error",
not good engineering practices. Even I love the enthusiastic, never-give-up mentality, I will plan some coaching session
to mature them.
|BR|
I did the same with several CodeAI agents. I failed! They keep responding enthusiastically, promise me
improvements and continue as usual. Apparently, virtual coworkers have to mature in a different way.

It's truly wonderful that LLM have come so far in a couple of years. More and more they can take over light coding jobs
---and I glad about that.
|BR|
I'm equally grateful that they helped me to understand how 'Agentic' works, and assisted to configure my lab MCP
environment. Still, it was shocking to read the MCP-conversation; it did mis the engineering discipline, we need.

To make a long story short: Yes, it helps. But, for now, I will not redeem my *deterministic* build scripts for the "try
and error", stochastic approach of the current agents.


See you soon; keep using your own synapses too --- ALbert
